# HiRes Buddy — дизайн

Дата: 2026-10-16. Статус: черновик на утверждении.

## Зачем

macOS отдаёт звук в Bluetooth-наушники только через SBC или AAC. Наушники с LDAC (Sony WH-1000XM4 и другие) на Mac работают в AAC. Пользователь хочет слушать музыку с Mac в LDAC (и aptX HD, если наушники его поддерживают) из любого плеера, с переключением качества на лету и видимым статусом потока.

Экспериментально доказано (16.10.2026, macOS 15.7.4, Apple Silicon, WH-1000XM4): обычное приложение может открыть AVDTP-каналы к наушникам, договориться об LDAC и стримить звук. Прототип — `player/ldacplay.m`. Этот документ описывает превращение прототипа в постоянную программу.

## Что это

Приложение в строке меню, в духе AirBuddy. Иконка наушников; по клику — панель.

Когда LDAC включён, в системе появляется устройство вывода «<Имя наушников> (LDAC)». Любой плеер (VOX, Spotify, браузер) играет в него, приложение кодирует звук в LDAC и отдаёт в наушники. Пользователь не меняет свои плееры.

## Цели

1. Звук с любого приложения Mac в наушники по LDAC без потерь до кодера.
2. Переключение качества LDAC (990 / 660 / 330 / Авто) на лету, без обрыва звука — чтобы можно было вслушиваться в один и тот же фрагмент.
3. Первый экран панели — статус потока для отладки: кодек, частота, битрейт, пакеты, провалы, аптайм.
4. Любые наушники с LDAC; aptX HD как второй кодек.
5. Клавиши громкости Mac работают.

## Не-цели (сейчас)

- ANC, эквалайзер, другие фирменные настройки Sony/прочих.
- Микрофон / звонки через LDAC. HFP остаётся у системы как есть.
- Поддержка Intel Mac и macOS < 15 (не проверяется; может работать).
- Статистика качества связи (RSSI, ретрансмиты) — отдельная секция позже, когда поток стабилен.
- Кнопки громкости на наушниках (AVRCP) — второй этап.

## Анти-цели

- Приложение не должно оставлять наушники в «полумёртвом» состоянии (HFP без A2DP) после выключения LDAC или выхода: выключение обязано вернуть системный A2DP (достаточно разорвать и восстановить baseband-соединение).
- Не должно ломать работу наушников с телефоном или другими устройствами.
- Никакого ресемплинга или обработки звука кроме: применения системной громкости и даунсемплинга >96 кГц (предел LDAC).

## Как это устроено

### Компоненты

```
┌─────────────────────┐   PCM (CoreAudio)   ┌──────────────────┐   L2CAP   ┌──────────┐
│ Виртуальное         │ ───────────────────▶│ HiRes Buddy.app  │ ─────────▶│ Наушники │
│ аудиоустройство     │                     │ menubar + стример│           │ (LDAC)   │
│ (BlackHole, driver) │                     │ + helper-процесс │           └──────────┘
└─────────────────────┘                     └──────────────────┘
```

1. **Виртуальное аудиоустройство.** Форк BlackHole (GPL-3; личное использование). Собирается как отдельный HAL-драйвер с собственным именем и bundle id, 2 канала, 24-бит/float32, частоты 44.1/48/88.2/96 кГц, с контролем громкости. Устанавливается в `/Library/Audio/Plug-Ins/HAL/` (один раз, с запросом пароля через приложение). Имя устройства в системе: «<Имя наушников> (LDAC)»; если имя нельзя менять динамически в HAL — «HiRes Buddy (LDAC)».
2. **Стример** (внутри .app, Swift + ObjC-мост к существующему коду): читает PCM с виртуального устройства (CoreAudio input side BlackHole), применяет громкость устройства, кодирует libldac, пакует RTP, пишет в транспортный L2CAP-сокет. Логика AVDTP (DISCOVER → GET_CAP → SET_CONF → OPEN → START, SUSPEND/CLOSE) — перенос из `ldacplay.m`.
3. **Helper-процесс** `hiresbuddy-transport` (внутри бандла): открывает второй L2CAP-канал на PSM 0x19 (транспорт) и передаёт сокет приложению через unix-socket + SCM_RIGHTS. Нужен потому, что bluetoothd даёт одной XPC-сессии один канал на PSM.
4. **Панель** (SwiftUI, `MenuBarExtra`).

### Ключевые механизмы (уже проверены в прототипе — не переизобретать)

- Открытие L2CAP на уже подключённом устройстве: **только** через приватный `CBClassicPeer`: `[[dev classicPeer] setConnectL2CAPCallback:^(CBL2CAPChannel *ch, long code)]` + `[peer openL2CAPChannel:0x19]`. Публичный `IOBluetoothL2CAPChannel` на подключённом устройстве открывает и тут же закрывает канал (см. `player/ldacplay.m`, комментарии).
- У `CBL2CAPChannel` есть `_socketFD` (SOCK_STREAM). Каждый `write()` = один L2CAP SDU, наушники принимают RTP-пакеты именно так.
- Перехват A2DP у macOS: `closeConnection` на устройстве, затем сразу `openL2CAPChannel:` — bluetoothd поднимает ACL и шлёт наш connect первым, раньше своего A2DP. Если первая попытка даёт 704/454 — повтор каждые 2 с до 8 раз.
- Во время потока bluetoothd раз в ~10 с пытается поднять свой A2DP; наушники ему отказывают, но ответ может прилететь в наш сигнальный канал — игнорировать, не рвать поток.
- Info.plist обязан содержать `NSBluetoothAlwaysUsageDescription`.

### Поток, качество и Авто

- Кодер: libldac (AOSP, Apache 2.0), `ldacBT_init_handle_encode(mtu=679, eqmid, STEREO, fmt, sf)`. Переключение 990/660/330 — `ldacBT_set_eqmid`, на лету, поток не прерывается.
- **Авто**: старт с HQ (990). Признак провала — переполнение сокета (`write` блокируется/EAGAIN дольше N мс) или рост очереди; при 3 провалах за 10 с → ступень ниже. При 60 с без провалов → ступень выше. Текущий битрейт виден в панели.
- Упреждение буфера 250 мс.
- **Частота следует за источником**: частота виртуального устройства = то, что выставил плеер (или система); стример договаривается с наушниками о той же частоте (44.1/48/88.2/96). Смена частоты = переинициализация кодера и реконфигурация AVDTP (короткая пауза, допустимо). Выше 96 кГц — даунсемплинг системой до 96.
- **aptX HD**: кодер `aptx_hd` из FFmpeg (libavcodec, LGPL). Выбирается, если наушники объявили vendor codec Qualcomm (vendor 0x00D7, codec 0x0024) и пользователь выбрал его. Не тестируется на XM4 (нет поддержки). Реализуется после LDAC.

### Панель

Первый экран (статус потока):
- Наушники: имя, подключены/нет, заряд (если доступен через IOBluetooth battery или AVRCP — иначе не показывать).
- LDAC: тумблер вкл/выкл.
- Кодек и режим: «LDAC · 96 kHz · 990 kbps» / «AAC (система)».
- Качество: сегмент 990 / 660 / 330 / Авто.
- Статистика сессии: пакетов, провалов (переключений вниз), аптайм, текущая задержка буфера.
- Выбор устройства: список сопряжённых наушников с LDAC/aptX HD.

Настройки (вторая вкладка/окно): автоперехват при подключении, качество по умолчанию, запуск при входе, установка/удаление драйвера.

### Громкость

Клавиши Mac меняют громкость виртуального устройства; стример читает её и применяет перед кодером (float, 24-бит — без слышимых потерь). Кнопки наушников — второй этап (AVRCP, PSM 0x17; риск, что bluetoothd не отдаст канал).

### Выключение / выход

Выкл LDAC: SUSPEND+CLOSE AVDTP, закрыть каналы, `closeConnection` + дать системе переподключиться (или `openConnection`) — macOS сама поднимет AAC. Вернуть прежнее устройство вывода. Выход из приложения делает то же самое.

## Ограничения

- Приватный API CoreBluetooth; может сломаться с обновлением macOS. Приложение должно явно сообщать «не удалось открыть канал» с кодом, не зависать.
- Без App Store, без нотаризации — локальная сборка, ad-hoc подпись.
- GPL для драйвера (BlackHole) — приемлемо для личного использования; при публикации учитывать.

## Что решено мной (можно оспорить)

- Виртуальное устройство присутствует в системе постоянно, имя фиксированное «HiRes Buddy» (BlackHole — статический HAL-плагин; динамическое появление/переименование — отдельный проект).
- Частота меняется только когда плеер сам переключает nominal sample rate устройства (VOX, Audirvana). Смена = CLOSE → новый handshake, пауза ~2 с, допустимо. Источники без управления частотой (Spotify, браузер) ресемплит macOS до текущей. AVDTP RECONFIGURE без обрыва — опциональный спайк на XM4.
- SCO (звонок, FaceTime, Siri) во время LDAC: SUSPEND по событию SCO-open, START по SCO-close; Авто-режим на этот интервал отключён.
- aptX HD тестируется на HUAWEI FreeBuds Pro 4 (есть у пользователя), если они объявят кодек Qualcomm в GET_CAP; если нет — aptX HD остаётся за флагом, без гарантии.

- Swift + SwiftUI для UI, ObjC для Bluetooth/кодера. Xcode-проект, не SPM-only (нужен бандл с helper и драйвер).
- BlackHole как основа драйвера, а не написание HAL с нуля.
- Helper-процесс для транспортного канала (а не попытка второй XPC-сессии в одном процессе).
- Авто-режим по признаку заполнения сокета, а не по RSSI (RSSI не показывает потери на линке).

2. Драйвер (форк BlackHole) + чтение PCM → стример. Звук из VOX в LDAC.
3. Menubar-панель: тумблер, качество, статус.
4. Авто-режим, следование за частотой, громкость.
5. Мультиустройство, aptX HD.
